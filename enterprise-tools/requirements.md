# 员工首页工具权限：场景 UX 与开发需求

版本：2026-10-27 · 需求确认稿

最新样式调整：以文末第 10 节“首页紧凑单行”、第 11 节“全部工具列表”及完整 UX 页右侧抽屉为准，替代前文首页两行及前七项规则。

配套原型：[employee.html](./employee.html)。顶部「权限展示场景」仅用于评审，不属于员工首页正式功能。

## 1. 确认范围

员工首页在搜索框下方、项目列表上方展示企业主已开放的工具。移除「常用工具」「工具专区」等模块标题，仅呈现图标和工具名称。员工侧不展示权限开关、配置入口、关闭的工具或锁定占位。

工具及固定顺序：组合提词 → 快捷提词 → 知乎新文。企业主控制当前企业内每位员工的可见权限。三个工具支持独立授权，才能覆盖单独开放任意工具的场景。

「知乎新文」点击后进入内部「知乎书单」页面，不配置外部 H5 跳转地址。页面样式参考用户提供的知乎书单截图。

本次交付为场景 UX 和前后端开发需求，非后端已完成或正式上线证明。

## 2. 场景 UX

工具权限用三位顺序表示：组合提词 / 快捷提词 / 知乎新文，1 为开放，0 为关闭。

| 场景 | 权限 | 员工首页展示 | 布局 |
| --- | --- | --- | --- |
| S01 | 100 | 仅组合提词 | 整行入口：左侧图标、中间名称、右侧箭头 |
| S02 | 010 | 仅快捷提词 | 整行入口：左侧图标、中间名称、右侧箭头 |
| S03 | 001 | 仅知乎新文 | 整行入口：左侧蓝色「知」字图标、中间名称、右侧箭头 |
| S04 | 110 | 组合提词、快捷提词 | 两列等宽，图标上、名称下 |
| S05 | 101 | 组合提词、知乎新文 | 两列等宽，图标上、名称下 |
| S06 | 011 | 快捷提词、知乎新文 | 两列等宽，图标上、名称下 |
| S07 | 111 | 三个工具全部展示 | 三列等宽，图标上、名称下 |
| S08 | 000 | 无工具入口 | 工具模块整体隐藏，项目列表上移，无空白占位 |

### 视觉与交互

- 工具区使用单个白色圆角容器，左右与搜索框、项目列表对齐；不再增加标题行和说明文字。
- 单工具使用紧凑整行入口，避免只占三分之一宽度或放大为宣传卡片；整行可点击。
- 双工具 / 三工具平均分配可用宽度，不保留已关闭工具的位置；每个图标与名称构成完整可点击区域。
- 建议容器圆角 12px、内边距 12px；图标 40–42px；名称 12–14px。单工具整行高度约 68–72px，多工具容器高度约 88–92px。以原型和实际屏幕适配为准。
- 适配 320 / 375 / 414px 屏宽，名称不截断、不换行；触控区域至少 44×44px，支持键盘聚焦。
- 首页不出现「未开通」「请联系企业主」等权限提示。仅在用户通过旧链接直接访问受限页面时提示无权限。
- 组合提词、快捷提词沿用原有页面；知乎新文进入知乎书单。返回首页后保留项目筛选、搜索和列表位置。

## 3. 前端开发需求

### 3.1 权限驱动与动态排布

1. 从服务端获取当前企业、当前员工关系下的有效工具权限，不以本地开关作为授权依据。
2. 将允许的工具按固定顺序过滤为 visibleTools，按数量渲染 0 / 1 / 2 / 3 场景；图标与名称来自固定工具定义。
3. 不再使用同一个提词权限同时决定两个入口，接入独立组合提词与快捷提词权限。
4. 初次加载权限期间不展示工具；可暂时保留一个紧凑骨架，避免闪现未授权工具。加载失败或身份无效时隐藏工具区，不将失败当作「全部开放」。
5. 用户重新进入首页时刷新权限。切换企业、退出登录或员工关系变化时立即清除旧权限与旧书单，不能沿用上一个企业的数据。
6. 点击工具入口和进入工具页时均检查最新可用权限；接口返回权限失效时清空相关内容，提示并返回首页。前端校验不替代后端鉴权。
7. 接口缺失某项权限默认关闭。显式返回 false 优先于旧字段，不得因兼容逻辑重新开启。

### 3.2 知乎书单页面

- 顶部返回 + 页面名「知乎书单」，保留参考图橙红渐变头图。
- 搜索框按作品标题搜索，支持键盘搜索、清空、无结果状态；新查询重置分页。
- 排序：更新时间最新优先、更新时间最早优先、盐选点赞从高到低。
- 筛选：标签筛选（本期单选）；标签候选由接口返回。搜索、标签和排序共同生效。
- 卡片包含作品标题、最多两行简介、标签、作者、作者获赞 / 粉丝、更新时间及五项数据：盐选点赞、盐选评论、回答点赞、回答评论、回答收藏。
- 已知统计为 0 时显示 0，未知值显示「—」；不将缺失数据补成 0。暂无作者等非必要内容可省略。
- 支持分页、加载更多、刷新、请求失败重试。筛选和排序作用于全部匹配数据，不能只处理当前已加载列表。
- 多次搜索或筛选时只接收最后一次请求结果，防止较早请求覆盖新条件；分页失败保持已有卡片，重试不跳页、不重复插入。
- 权限未开通、官方源未配置、书库暂无作品、搜索无结果、请求失败分别呈现对应状态。
- 卡片暂作为书单信息展示，不新增申请、提词、复制或作品详情跳转流程。
- 原型中的示例作品和数字仅用于样式评审，不作为正式数据写入。

## 4. 后端开发需求

### 4.1 权限模型与企业主配置

- 按「企业 ID + 员工关系 ID + 工具标识」存储独立权限，不使用全平台用户 ID 作为唯一授权维度。
- 工具标识固定为 compose_prompt、quick_prompt、zhihu_article；新员工默认关闭，企业主明确开启后生效。
- 企业主员工权限管理中提供三个独立工具开关。可复用现有单员工 / 批量操作框架，批量接口使用员工关系 ID 列表。
- 单次提交校验全部员工均属于当前企业且可管理；存在无效或越权对象时整批失败，不允许静默部分成功。校验通过后事务保存，返回最终权限版本。
- 企业主只能管理自己企业内员工的权限。员工不能调用权限保存接口。
- 所有工具业务接口及书单接口必须重新校验有效员工关系和工具权限；仅隐藏入口不足以限制访问。
- 开关变化记录操作人、企业、员工关系、工具、修改前后值、时间与权限版本。
- 默认关闭不追溯清空历史任务或历史记录；历史数据访问沿用原有业务规则。

### 4.2 旧权限迁移与兼容

当前仓库使用 can_quick_prompt / quick_prompt_enabled 同时控制组合提词与快捷提词，已有 quickPromptPermissionSave 接口及字节项目权限前置规则。

- 迁移时按旧权限生成两项独立权限：旧开启 → 两项开启；旧关闭或缺失 → 两项关闭。知乎新文默认关闭。
- 迁移后 compose_prompt 和 quick_prompt 独立保存；不能每次读取旧字段时覆盖新配置。
- 新保存接口沿用现有字节项目依赖校验。确有项目依赖时返回明确错误，不隐式开放项目；若需联动开项目，复用已确认的显式授权流程并原子保存。
- 旧客户端仅能表达「两项同时开关」，与新独立授权不完全兼容。发布时建议要求刷新 / 升级客户端；服务端应对旧写接口增加版本校验，避免覆盖已拆分权限。
- 旧读取字段可暂按“两项都开启才返回开启”兼容，不能将两项取或后开放旧客户端两个入口。最终下线时间由发布计划确认。

### 4.3 官方书库

- 接入经确认的知乎官方 / 授权作品数据源，不凭页面截图构造线上作品数据。
- 支持标题搜索、标签筛选、全量结果排序和分页；同更新时间按作品 ID 排序以保持顺序稳定。
- 存储作品唯一 ID、标题、简介、标签、作者信息、五项统计、作品更新时间和数据同步时间；统计缺失保留 null。
- 缓存必须带上数据源和必要的企业范围，权限检查不得被缓存绕过。设置可配置同步周期，失败保留上次有效数据并记录异常。
- 不接受客户端提交任意任务 ID 来选择数据源；由服务端配置已确认的官方源，按当前身份返回可访问数据。

## 5. 建议接口契约（新增提案，待后端确认）

以下路径和结构是开发建议，不表示现有后端已提供。

### 员工有效权限 GET /api/v1.enterprise.tools/permissions

请求身份从登录态获取，不由客户端指定企业或员工。

```json
{
  "code": 1,
  "data": {
    "permission_version": 12,
    "tools": {
      "compose_prompt": true,
      "quick_prompt": false,
      "zhihu_article": true
    }
  }
}
```

### 企业主保存 POST /api/v1.enterprise.staff/toolPermissionsSave

```json
{
  "ids": [634],
  "expected_versions": { "634": 12 },
  "tools": { "compose_prompt": true, "quick_prompt": false, "zhihu_article": true }
}
```

tools 为局部更新，未传字段保持原值；不接受空对象和未知工具。若 expected_versions 与当前版本不一致，返回版本冲突，前端重新读取并让企业主确认后再提交。成功响应返回受影响员工关系及其最新工具权限、版本，不能仅回显请求。

### 书单 GET /api/v1.enterprise.tools/zhihuBooks

参数：keyword（标题关键词）、tag（单个标签 ID）、sort（updated_desc / updated_asc / yanxuan_likes_desc）、page、limit。limit 默认 20，最大 50；tag 不存在或 sort 不合法时返回参数错误。

```json
{
  "code": 1,
  "data": {
    "list": [{
      "id": "official-book-id",
      "title": "作品标题",
      "intro": "作品简介",
      "tags": [{ "id": "romance", "name": "言情" }],
      "author": { "name": "作者名", "likes": 237000, "followers": 21000 },
      "updated_at": "2026-10-27T18:27:00+08:00",
      "metrics": {
        "yanxuan_likes": 1, "yanxuan_comments": 1,
        "answer_likes": 0, "answer_comments": 0, "answer_favorites": null
      }
    }],
    "total": 1, "page": 1, "limit": 20,
    "available_tags": [{ "id": "romance", "name": "言情" }],
    "synced_at": "2026-10-27T18:30:00+08:00"
  }
}
```

available_tags 返回当前书库可用标签，不能只从本页结果提取。示例仅说明结构，不是生产数据。

错误语义：未登录、无有效企业关系、无工具权限、数据源未配置、参数错误、版本冲突、源服务异常；具体业务错误码与项目现有规范统一。无结果是成功且 list 为空，不作为接口失败。

## 8. 工具数量扩展方案（本次补充）

首页仍无模块标题，始终按员工实际有权限的工具数量排布，新增工具不改变核心规则。

| 开放数量 | 首页展示 | 交互 |
| --- | --- | --- |
| 0 | 整块隐藏 | 无空白占位 |
| 1 | 整行，图标 + 名称 + 右箭头 | 整行点击 |
| 2–3 | 同行等分 | 点击各工具 |
| 4 | 一行四列 | 不做横向滑动 |
| 5–8 | 每行四列，最多两行；末行从左向右连续排布 | 不强行拉大末行图标，不保留关闭项占位 |
| 超过 8 | 首页前 7 个已授权工具 + 第 8 格「全部工具」 | 打开内部全部工具页，按四列宫格展示全部已授权工具 |

### 为什么采用宫格

横向滑动会将部分工具藏在屏幕外，员工不易发现；左右翻页也增加操作。纵向单行列表在工具多时过高，会将项目列表推离首屏。因此，首页采用最多两行的四列宫格，大量工具通过明确的「全部工具」入口进入独立页面。

5 个或 6 个工具时，末行保持左对齐及同样的列宽，避免为了填满空间而把相同工具渲染成不同尺寸。卡片内各图标与文字仍保持居中。

### 前端补充

- 先过滤权限、停用项和客户端不支持项，再计算数量及首页前 7 个，不能先截断再过滤。
- 「全部工具」是导航入口，不是一项企业主权限，不计入开放工具数量；数量小于等于 8 时不显示。
- 全部工具页沿用同一权限源、固定排序和点击规则，返回保留首页上下文。权限降到 8 个以内时首页自动移除「全部工具」。
- 全部工具页打开期间如权限关闭，立即在下一次权限刷新后移除对应工具；失去全部权限时显示简洁空态和返回首页入口。
- 首期扩展布局按工具短名称最多 6 个汉字适配，后台配置时校验；更长名称需提供短名称，不将文字压缩至不可读。
- 首页不自动轮播、不横滑、不新增员工自行排序配置。未来确有个人常用需求时另立需求。

### 后端补充

- 工具目录按 tool_key、display_name、icon_key、sort_order、status 管理；有效可见列表结合企业授权、员工授权和工具启用状态计算。
- tool_key 为权限主键。工具路由由客户端已注册映射确定，接口不下发可执行脚本或未经校验的任意跳转目标。
- 同 sort_order 时以 tool_key 作为稳定排序；首页和全部工具页使用同一顺序。
- 可在当前权限接口中补充有序 tools 列表；需在联调前确定最终结构并统一替换文档第 5 节的三工具对象示例，避免两种结构混用。默认仍只开放已实现的三个工具，原型的工具四至工具十不属于正式目录。

### 扩展验收

覆盖 4、5、6、8、9、10 个可见工具；特别验证 8→9 时第八格变为「全部工具」，9→8 时恢复为真实工具。首七项必须是过滤后排序结果；全部工具页完整展示第八项及其后工具，无遗漏、重复。所有数量场景在 320px 屏宽下不横向溢出。

以上为对前文三工具布局规则的扩展；正式工具数量和目录以实际上线功能为准。


## 9. 平台后台配置与完整页面需求抽屉（补充确认）

完整场景 UX 页已集成右侧可收起的开发需求抽屉，含场景规则、后台配置、前端、后端 / 验收四个标签。开发可边切换权限场景边查看需求；抽屉和场景切换器属于评审工具，不进入正式员工首页。

后台统一配置每个工具的：唯一标识、前端名称、图标、适用端（企业主 / 员工，可多选）、企业主跳转、员工跳转、注意事项、排序、启用状态、开放企业范围。选择哪一端，就必须填写该端链接；两端允许使用不同链接。

链接支持已注册内部页面和平台允许域名下的 HTTPS 页面。知乎新文当前仍使用内部知乎书单页。后台配置与服务端校验通过后才能启用；无效链接不发布。前文仅允许固定客户端映射的限制更新为此规则。

注意事项不堆在首页：内部目标页提供「使用说明」入口；外部链接在跳转前的说明弹窗展示，有说明时确认后跳转。

企业主自用工具可见范围由后台控制；企业主给员工授权时只能操作已对该企业开放且适用员工侧的工具。企业主可见不意味着员工自动可见，员工最终权限必须同时满足后台启用、开放企业范围、适用员工侧、企业主授权。

有效列表返回当前端身份对应的名称、图标、已校验链接、注意事项、排序和配置版本。全部工具页使用同一有效列表，10 个真实工具按 4＋4＋2 展示；首页前 7 个加导航入口，不少算、不重复。


## 10. 首页紧凑单行（最新确认）

工具区过大，会挤占项目列表。首页改为最多一行，完整工具集合仍在独立页面展示。

- 0 个：整体隐藏。
- 1 个：图标 + 名称 + 右箭头的紧凑整行，约 56px 高。
- 2–4 个：同行等分，28px 图标在上、名称在下，整个区域约 68px 高。
- 5 个及以上：首页只展示排序前 3 个 +「全部工具」，同样约 68px 高。
- 全部工具页保留四列宫格、40–42px 图标；10 个工具按 4＋4＋2 完整展示。
- 无标题、不横滑、不在首页展开多行；后台排序和独立授权规则不变。
- 特别验收 4↔5 个时导航入口切换；先过滤权限再取前 3 个，不遗漏隐藏工具。全部页中第 4–10 个实际工具都需出现。

本节取代前文“首页前 7 个 + 全部工具”“首页最多两行”及首页图标 40–42px 的规则。右侧抽屉已同步更新。


## 11. 全部工具列表（最新确认）

点击首页「全部工具」后，使用纵向列表，不再使用宫格。10 个工具对应 10 行，页面自然滚动。

- 每行：36px 图标、工具名称、右箭头，整行可点击；建议行高 60–64px。
- 列表统一白色圆角容器，行间细分隔线，最后一行无分隔线。
- 保持后台排序和当前员工有效权限过滤，首页与全部页顺序一致。
- 点击执行该端配置的目标链接；返回首页保留原来的筛选与滚动位置。
- 无工具时展示空态及返回入口，权限变化时刷新列表。

本节替代前文全部工具页“四列宫格 / 4＋4＋2”的样式要求；首页仍按第 10 节保持紧凑单行。右侧抽屉已同步。

## 13. 后台展示位置、图标上传与排序（最新确认）

- 每个工具的前端展示位置只能单选：企业主（owner）或员工（employee）。取消多选，不允许一个工具同时展示两端。
- 每个工具只保存一组链接：target_type + target，链接随选定展示位置生效。此前“两端独立链接”规则作废。
- 图标配置改为上传，支持 PNG / JPG / WebP，≤2MB，建议 128×128px 方图；提供预览、替换、移除及失败提示。新增必须上传；编辑保留已有图标，失败不覆盖。
- 正式上传由服务端校验真实文件类型、大小并返回素材 ID / URL，保存只引用成功的素材。UX 上传只在浏览器本地读取与预览。
- 排序统一为数值越大越靠前；同值按工具标识稳定排序。后台列表、员工首页、全部工具页使用同一规则。
- 后端字段 display_position 只接受 owner / employee 单值，拒绝多选数组；现有多端记录上线前由平台管理员明确选择位置后迁移，不能自动扩大或猜测显示位置。

本节覆盖前文适用端多选和两端链接的旧方案。
